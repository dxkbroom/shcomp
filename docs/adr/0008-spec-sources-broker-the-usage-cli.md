# Spec sources broker the `usage` CLI

A `kind = "usage"` source names a command that prints a usage KDL spec, or a file that holds one. shcomp does not parse that spec and does not render candidates from it: it asks `usage generate completion <shell> <command> --usage-cmd <argv> --cache-key <key>` for a script at load time, caches that script per resolved binary like any other source, and leaves completion to the `usage` CLI at Tab time. The alternative — implementing the spec→script rendering in shcomp — would make shcomp a second completion engine for the one format it can defer on, and would drift from `usage`'s own rendering (its caching, its `complete … run=` handling, its shell quirks) on every release. The `--cache-key` we pass is hashed from the executable's real path, mtime, and size, so the spec-producing command runs once per binary and a version switch asks for a different key. The costs are explicit: `usage` must be on `PATH` wherever a spec-sourced completion runs, and the spec cache lands in `$XDG_CACHE_HOME/usage`, outside `shcomp clean`. Both are documented, and a missing `usage` is an error that names the install step rather than a fallback.
