# `doctor --check` asks the user's real shell

Whether the loading line works is a property of the user's interactive shell, not of a file shcomp can parse: `fpath` and `fish_complete_path` are assembled by dotfiles, plugin managers, and frameworks that shcomp has no business interpreting. So `doctor --check` starts `zsh -i` and `fish` with a timeout, stdin from `/dev/null`, and a sentinel around the printed path list, and reads back the directories the shell would actually search. That answers three questions no static check can: whether shcomp's directory is on the path, whether a foreign `_cmd` or `cmd.fish` earlier on the path shadows a shim, and whether a stale static `_shcomp` from v0.0.1 is still lying around. The probe runs the user's startup files, which may be slow or print noise, so it lives behind `--check`, which already means "run things", and a timeout or a missing shell is a warning rather than an error. Plain `doctor` stays fast and side-effect free. `install` and `add` do not start a shell to decide whether to print the loading line; they rely on cheaper evidence recorded by earlier loads and probes (ADR-0011).
